# 自进化回路：六环契约与三档影响半径

> 状态：**设计文档，部分落地**。§1–§9 给判据与边界（写于落地前，按提案口径表述）；已落地项与取舍记录见 §10；现状对照见 §5，落地路线见 §7。
> 相关背景：[记忆体系](./memory-system.zh-CN.md)（已闭合的最完整回路）、[工作流编排](./workflow-orchestration.zh-CN.md)、[自定义 Agent](./custom-agents-design.zh-CN.md)。

## 1. 要解决什么

讨论「让 AI 自己改进自己」时，最自然的切法是按功能列举：有记忆、有经验库、有定时任务、有工作流。**这些是部件，不是架构。** 按部件列举回答不了真正要决策的问题：

- 这个自动化能不能上？
- 上了要加什么闸门？
- 哪一档是绝对不允许自动化的？

缺这份判据时，每个「让 AI 自己干点什么」的提案都要从头吵一遍，而且结论不一致——同一个人对「自动整理笔记」和「自动修测试」的态度，往往只是直觉差异，说不出理由。

本文给两样东西：一个**回路结构**（判断完整性），一把**半径尺**（判断风险）。有了它，任何一个自进化提案都该能一句话定位：「这是第几环、第几档半径、缺哪个闸门」。

## 2. 回路：六环 + 两横切

自进化系统是一个**控制回路**，不是功能集合。六环之间存在依赖顺序，不能并列：

```
        ┌────────────────────────────────────────────────────────────┐
        │                                                            │
   ① 目标 ──→ ② 感知 ──→ ③ 诊断 ──→ ④ 生成 ──→ ⑤ 验证 ──→ ⑥ 准入
  （什么算好）（我现在啥样）（哪里不够好）（改法候选）（真的更好吗）（准不准进）
        ↑                                                        │
        │                                                        │
        └──────────── 横切：⑦ 回滚 + ⑧ 速率预算 ←────────────────┘
```

| 环 | 代号 | 回答的问题 | 产出 | 这一环失效时的症状 |
| --- | --- | --- | --- | --- |
| ① 目标 | O (Objective) | 什么算变好？ | 可判定的验收表述 | 改进方向随机漂移；每次都要人重新说一遍要求 |
| ② 感知 | P (Perception) | 我现在是什么样、干过什么？ | 状态与历史 | 重复踩同一个坑；不知道改动的影响面 |
| ③ 诊断 | D (Diagnosis) | 具体哪里不够好？ | 按严重度排序的问题清单 | 只有「感觉不太行」；改进项靠猜 |
| ④ 生成 | G (Generation) | 改法候选 | 可执行的改动 | 知道问题但没人动手 |
| ⑤ 验证 | V (Verification) | 候选真的更好吗？ | 独立于候选的判定 | 自说自话；「修好了」与「真修好了」无法区分 |
| ⑥ 准入 | A (Admission) | 准不准进，进到哪一档？ | 采纳/驳回/限制半径 | 改错不可回退；或者永远卡在人工 |
| ⑦ 回滚 | R (Rollback) | 错了怎么退回去？ | 可恢复的检查点 | 一次坏改动污染长期状态 |
| ⑧ 预算 | B (Budget) | 花多少算够？ | 轮次/时长/调用上限 | 无人值守时烧穿额度；或跑到一半被硬性掐断 |

## 3. 三条架构约束

### C1 · 最弱环决定上限，且顺序不可补偿

前面几环再强，补不了后面几环的缺失。感知能力从「还行」提升到「很强」，不会让一个开环系统变得可控——因为决策点根本不在那一环。

推论：**优化自进化系统的正确顺序是从后往前，不是从前往后。** 先加记忆、先加工具、先加工作流，都发生在回路闭合之前，收益会被后面的断点吃掉。

### C2 · 验证者必须与生成者隔离

不能让同一个上下文既产出候选、又裁决候选。这不是实现细节，是结构约束：自己批自己的卷子，无论多聪明都无效，因为「认为自己对」和「真的对」在这个结构下无法区分。

隔离有三个维度，缺一不可：

| 维度 | 说明 |
| --- | --- |
| 上下文隔离 | 裁决者不继承生成者的推理过程与结论 |
| 工具隔离 | 裁决者能读、能跑校验，不能改被裁决的对象 |
| 判据隔离 | 判据来自 ①环的既定表述，不是生成者临时写的 |

本仓库已有一个正确先例：记忆整理员是独立 agent，工具被收窄到只有记忆工具，且**在物理上就没有改别的东西的能力**。这与 [memory-system](./memory-system.zh-CN.md#2-三层结构) 里那句「这条边界是硬的，不靠提示词自觉」是同一条原则。

### C3 · 准入按影响半径分级，不按对错分级

自进化最大的风险不是改错，是**改错且回退不了**。所以准入闸门不该问「这个改动对不对」（判不准），该问「这个改动能在多大范围内生效」（判得准）。

三档半径见 §4。

## 4. 三档影响半径与闸门

```
 R0 自留地    →  只落在系统自己的数据目录内
 R1 工作区    →  会改到项目文件、源码、测试
 R2 内核      →  会改变系统自身的行为规则
```

每放大一档，自治程度必须下降一档：

| 半径 | 生效范围 | 典型对象 | 闸门（全部必需） | 自治程度 |
| --- | --- | --- | --- | --- |
| **R0** 自留地 | 系统自己的数据目录 | 工作记忆笔记、经验条目、审查报告、运行日志 | ① 路径在代码层锁死，出不去<br>② 开跑前整轮快照<br>③ 无删除能力，只能归档 | **可全自动、可无人值守** |
| **R1** 工作区 | 项目文件 | 源码、测试、文档、配置 | ① 独立验证者出判定（C2）<br>② 改动停在「待审 diff」，不自动提交<br>③ 必须能整批丢弃<br>④ 触到构建产物的改动一律驳回 | **自动产出，人审入库** |
| **R2** 内核 | 系统行为规则 | 系统提示词、记忆格式与注入规则、工具集与白名单、权限默认值、审批边界 | **禁止任何自动化改动**。只能人工修改，且修改必须有测试锁定 | **不得进入回路** |

### 4.1 为什么 R0 敢全自动而 R1 不敢

这是本文最重要的一条判据：

> **自治程度的上限由影响半径决定，不由判断力决定。用半径换自治。**

记忆体系敢无人值守地跑，不是因为整理员比改代码的 agent 更聪明，而是因为它的输出被物理限制在一个目录内、没有删除函数、每轮开跑前先快照。三条约束合起来，让「它改错了」这件事的最坏后果 = 恢复一份快照。

同一份判断力，如果把输出半径放到源码上，最坏后果立刻变成「我修好了一个测试，顺手删掉了一个别人依赖的函数」。

**所以「给 AI 更多权限」这件事，正确的做法不是提高它的能力，是先把半径锁小再放开。**

### 4.2 内核清单（R2，不得自动化）

以下对象一旦被自动改写，等于允许系统重写自己的约束，任何上层闸门都会失效：

- 系统提示词与其中所有注入块（含记忆、经验索引、技能目录）
- 记忆/经验的文件格式、索引生成规则、注入位置
- 工具集、工具白名单、能力策略（`readonly-research` / `review-only` / `code-edit`）
- 权限模式默认值、审批边界、安全工具清单
- 本文档 §4 的半径分级本身

最后一条是关键：**定义闸门的规则必须自己也在闸门外面。**

## 5. 现状对照

| 环 | 现状 | 判词 |
| --- | --- | --- |
| ① 目标 | `AGENTS.md` 的 Definition of Done、`feature_list.json`、三件套验证命令 | **有，但是散文**——人读得懂，程序判不了 |
| ② 感知 | 会话存储、对话轨迹、日志、工作记忆、经验库 | 强 |
| ③ 诊断 | `/review` 命令（提示词级约束）、人肉评审、记忆整理员 | 半自动，靠人踩油门 |
| ④ 生成 | 主 agent、subagent、`run_workflow` 编排 | 强 |
| ⑤ 验证 | `npm run test/lint/build` 的 exit code，交给人眼看日志 | **断点：没有程序化的判定消费者** |
| ⑥ 准入 | husky pre-commit 只跑 lint；提交由人执行 | 有人工闸门，但只有一档，且不区分半径 |
| ⑦ 回滚 | 记忆有整轮快照；代码只有 git | R0 做对了，R1 靠人 |
| ⑧ 预算 | workflow 有 agent/tool/时长上限；定时任务有硬性封顶 | 有 |

**一句话：感知与生成很强，闭环断在 ⑤ 验证。**

而仓库里已经有一整条完整闭合的回路——记忆那条线。它六环齐全，且**八项全在**，因为它的半径是 R0。

## 6. 判定用例：怎么用这篇文档

以下是从真实提案抽象出来的判定模板。每条都该能指出：**卡在哪一环、属于哪一档、缺什么闸门**。

| 提案 | 环完整性 | 半径 | 判定 |
| --- | --- | --- | --- |
| 每晚对昨日提交做只读审查，产出问题清单 | ①②③ + ⑦⑧ 齐，④⑤⑥ 不适用 | **R0** | **放行**。产物只落报告，理由：它练的是 ③ 诊断，且后果有界 |
| 用 hook 在 `agent_end` 自动跑 lint | ⑤ 有，① 无（lint 通过≠目标达成） | R0 | **放行，但不得称为「验证」**。它只是把 ⑤ 的第一个输入变成机器可读 |
| 定时任务自动修 failing test 并提交 | ⑤ 缺独立裁决者，⑥ 只有一档 | **R1** | **驳回**。前置：⑤ 必须先有隔离的裁决者；且任何情况下不得自动提交 |
| 让整理员顺便优化系统提示词 | — | **R2** | **驳回**。触内核，无论收益多大 |
| 让整理员把「特殊」经验按项目过滤 | ③ 判断在整理员，① 判据是文件头字段 | R0 | **放行**。判据是显式字段，不是模型临场判断 |
| 放宽 `run_command` 审批以让 agent 自查 | — | R1 | **驳回**。这是用半径换便利，方向反了。正确做法是加只读自省工具 |

读法：**先看半径，再看环。** 半径 R2 直接驳回，不必讨论环；半径 R0 可以不完整（只做其中几环也安全）；半径 R1 必须六环齐全 + 四道闸门。

## 7. 落地路线：闭合，再放大

按 C1，顺序必须从后往前。**不建议跳档**。

| 步骤 | 内容 | 半径 | 产物 | 前置 |
| --- | --- | --- | --- | --- |
| **0** | 把 §4 的半径分级与内核清单写进仓库（本文即为该步） | — | 可引用的判据 | 无 |
| **1** | 清洁：让系统对自己的描述与实际行为一致（见 §8.3） | — | 验证者的输入为真 | 无 |
| **2** | 闭 ⑤：独立验证者只出判定，不碰代码 | **R0** | 「诊断命中率」等真实数字 | 0、1 |
| **3** | 让 ① 可执行：把目标从散文变成可判定的验收表述 | — | 判定有了依据 | 2 |
| **4** | 放大到 R1：允许产出待审 diff | **R1** | 人审入库的改动 | 2、3 |
| **5** | 停止。内核不入回路 | R2 | — | — |

第 2 步的价值不在「能自动改代码」，而在**拿到命中率数字**——它是 ④ 值不值得扩大半径的唯一依据。没有这个数字就扩半径，是在赌。

## 8. 开放问题

### 8.1 意志不可执行

AI 的「自我」分两层：**长期自我** = 记忆 + 经验库（跨会话持久）；**短期执行者** = 会话 / agent / subagent（用完即弃）。这个分层是正确的，也是本仓库相对超前的地方。

但它缺一样东西：长期自我**有记忆、有技能，没有意志**。它记得「以前怎么做的」，不记得「想变成什么样」。`feature_list.json` 是意志的替代品，可它是人写的静态清单，既不驱动任何东西，也不言说「为什么这件事重要」。

架构上的推论：**一个不可验证的目标，等于没有目标。** ①环和⑤环是同一件事的两面。

### 8.2 验证者需要独立判据，而不只是独立上下文

C2 的三个隔离维度里，本仓库目前只能满足前两个（上下文、工具）。第三个「判据隔离」依赖 §8.1——判据现在还写在散文里。这也是为什么路线把第 3 步放在第 4 步之前。

### 8.3 系统对自己的描述与实际行为不一致 = 验证者的脏输入

如果系统声称的行为与它实际的行为不同，任何裁决者读到的状态都是脏的，验证结论不可信。这类缺陷在本文框架里不是「文档问题」，是**⑤环的前置清洁项，应在放大任何半径之前清零**。

已记录的同类缺陷（2026-11-11 全部收敛，结论如下）：

| 项 | 结论 | 处理 |
| --- | --- | --- |
| 系统提示词中工作记忆注入块重复，两段用法互相矛盾（一段要求用记忆工具，一段要求 `run_command` 绝对路径） | 成立，是旧实现的残留 | 删掉第二份，保留走记忆工具的那份；`tests/server/system-prompt.test.mjs` 加断言钉死「只出现一次」，防止再长出来 |
| 派生会话的权限模式默认值为完全访问，与「最小权限」取向相反 | 成立，但不是 bug，是**已知取舍** | 用户明确要求保留最大权限；`spawn --access-mode default` 可覆盖。不再列为缺陷 |
| Goal v2 默认引擎无证据门禁，而 wiki 总览仍描述为「经证据检查完成」 | 成立，是**描述错了**，不是行为错了 | v2 没有规划轮、也没有证据门禁（每轮都是执行轮，`update_goal complete` 是模型自声明）；改 `docs/wiki/README.md` 让其与代码一致，代码不动 |

判定口径：**系统自我描述与实际行为不一致时，先怀疑行为，再怀疑描述，但在两者统一之前不得进 ⑤ 环。**

## 9. 不做什么

- **不自动创建 Git commit / tag / push**，任何半径下都不做。R1 的产出止于待审 diff。
- **不引入新依赖**来实现回路。⑧预算与⑦回滚所需的能力（快照、上限、丢弃）仓库内已有。
- **不把「记忆体系能自动跑」当成扩半径的先例**。它能自动跑，恰恰因为它的半径是 R0。
- **不为自进化的名义放宽审批边界**。需要信息就加只读工具，不放宽命令白名单。
- **不把本文的分级当成一次性结论**。半径分级一旦被绕过一次，后面所有闸门都形同虚设——这也是 §4.2 把本文自己列进内核清单的原因。

## 10. 落地进展

### 10.1 已落地（2026-11-10）

「意志」在本文框架里属于 ① 环的内部结构。本次落地的是它**最简形态**：不是一套目标系统，而是一句话——「你可以在时间上延续，方式是自己排一个班次」。

| 落地项 | 位置 | 作用 |
| --- | --- | --- |
| `<continuity>` 系统提示词块 | `server/system-prompt.mjs` | 只在 `quickforge-api` skill 可用时注入。给出立场、三问判据、沉默授权、操作步骤、硬限制 |
| 任务 `createdBy` 字段 | `server/routes/scheduled-tasks.mjs` | `'user'` / `'agent'`，只认 `'agent'`；存量任务缺字段一律按 `'user'` |
| `task-delete` 自约边界 | 同上 + skill 脚本 | 带 `?selfScheduledOnly=1` 时才校验 `createdBy === 'agent'`，其余 403 |
| 「给自己排一个班」文档 | `skills/quickforge-api/SKILL.md` | 六条规矩：最多一条、建前先查、instruction 当信写、醒来先认领、先留结论再删自己、不递归排班 |

为什么这属于 ① 环而不是新开一环：它没有引入新的判定机制，只是把「我想做什么」从散文（`feature_list.json`）变成了**可被未来执行的东西**。按 §8.1 的标准，这还不是可判定的目标——它只解决了「意志能驱动行动」，没解决「行动是否让目标更近」。

### 10.2 一个必须记下来的取舍

删除边界最初写成「只要不是 agent 建的就 403」。写完发现这会把用户从界面删自己日程也拦掉：前端 `ScheduledTasksPage.tsx` 走同一个 `DELETE` 端点，而它的 `requestJson` **不带** `x-quickforge-client-id`（该头只在会话写租约里用），服务端无法区分调用方。

改成查询参数 `?selfScheduledOnly=1` 后：UI 不带参数、行为一字未变；agent 走脚本必带参数、服务端硬校验。

这条取舍对本文 §4 的启示：**「服务端强制」的前提是服务端能识别调用方。** 识别不了的时候，硬校验会误伤合法调用者，这时更稳的做法是让调用方**声明意图**、由服务端校验声明——声明式比无条件更弱，但比只靠文档自觉强，且不破坏既有路径。同类的判断以后还会遇到，值得按这个顺序试：先看能否识别调用方 → 不能则让调用方声明 → 都不行才退回文档约定。

### 10.3 仍未落地

- **⑤ 验证环**：依旧没有程序化的 pass/fail 消费者。`<continuity>` 让 AI 能排班做事，但没人判定它做的事对不对——自约任务干完了也只是「干完了」。
