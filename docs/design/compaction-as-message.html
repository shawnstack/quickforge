压缩即消息：把「压缩点」做成会话里的一条真实消息

现在的分割线是推断出来的：服务端记下压缩瞬间的消息条数，前端再拿它跟渲染窗口做换算。只要有窗口滑动、流式消息、中间插入或截断回滚，推断就会漂 ——「线永远贴在底部」只是其中最显眼的一种。这份设计换掉整个前提：让压缩摘要成为一条真实的会话消息，线的位置就是它在消息数组里的下标。位置不再需要计算，也就不会再算错。

推荐：方案 B · 压缩即消息位置由消息日志保证模型上下文与界面同序结论：不是「也可以」，而是「应该」

01

问题复盘：线为什么一定会漂

不是某一次实现写错了，而是「把位置存成外部坐标」这个前提本身不成立。

一句话：压缩点的位置属于消息序列本身。现在它存在 session.contextCompaction 里，用的是「当时的数组长度」；而消息序列会移动（窗口裁剪、回合窗口、插入、截断）。两者一旦不同步，任何换算都只能靠猜 —— 猜错的表现就是线贴底、线下移、线消失，或线压在未摘要的内容上。

根因 1 · 位置是「那一刻的长度」

自动压缩写 occurredAtIndex = messages.length。按定义它就是当时的最后一条，所以压缩刚结束、后续内容还没产生时，线只能落在列表底部，下方是空的。

这就是「线一直在底部」最直接的原因：不是定位失败，而是它记录的就是「末尾」。

根因 2 · 两套坐标系

服务端记绝对下标；客户端渲染的是尾部窗口 + 回合窗口。前端要靠 messageBaseSeq 与 messageWindow.start 两次换算才能得到行号，任一层变化都要重算。

所以修好「贴底」之后，又冒出「线跑到上面」「线消失」。

根因 3 · 时间戳不是位置

为对抗窗口漂移，现在再用 compactedAt 比对消息时间戳当第二信号。但时间戳是首 token 时刻：压缩发生在某条消息流式期间时它早于 compactedAt，扫描会跳过它。

两个信号取 min 只是互相打补丁：补丁越多越难解释，也越难测。

根因 4 · 两份真相

模型上下文靠 buildAutoCompactLoopMessages() 从 compactedUpToIndex 切片，界面靠 history[] 画线，回滚靠 rollbackIndex < compactedUpToIndex 判断失效。

同一件事三处各自解释，任一处漂移就出现「界面有线、模型没有」或反之。

  ├─ messages 数组 不变（摘要不是消息）

方案 B 压缩点 = 消息，界面与模型读同一个下标

  ├─ 模型上下文：messages.slice(lastCompactionIndex)

  └─ 回滚：消息被截断 ⇒ 压缩自然失效（无需比较坐标）
02

设计原则

五条约束，用来判断后续每个细节该往哪边倒。

  1. 位置即真相：压缩点必须由消息序列的一个元素表达，不能由外部坐标表达。删掉这个元素 = 撤销压缩。
  2. 单一真相源：模型上下文、界面渲染、回滚判定读同一处（消息数组），不再各自解释一份元数据。
  3. 复用既有传输：不新增同步通道。插入/删除压缩点都走已有消息日志（replace / append）与 messages_replaced 帧。
  4. 模型与界面同序：用户看到的顺序就是模型读到的顺序，不出现「界面上方是被摘要的历史、模型却从中间 tail 开始」。
  5. 幂等可迁移：历史会话没有这条消息，迁移必须「读一次、补齐一次、重复执行无副作用」。
03

候选方案与取舍

A 是现状路线的极致修补，B 是换前提，C 是把坐标再抽一层。

方案做法位置稳定性代价 / 结论
A · 坐标推断
现状		服务端记 occurredAtIndex / boundaryIndex，前端结合窗口与时间戳换算行号，越界就 clamp。取决于窗口与信号质量永远在打补丁：贴底 → 抬到回合开头 → 压到流式行下面。测试只能锁住已知场景。否决。
B · 压缩即消息
推荐		摘要作为真实消息插入 tailStart；该消息自己渲染成「线 + 可展开摘要」；模型从这条消息开始读。恒等于消息下标一次中间插入（O(n) splice + 一次全窗口 replace 帧），换来「没有坐标可漂」。回滚/分叉/分享/多端全部复用消息机制。推荐。
C · 独立 marker 表新增 session_markers(session, seq, kind, payload)，用绝对 seq 引用压缩点。好（seq 稳定）多一个真相源：插入消息后 seq 要重编号；传输、回滚、分享各写一次。不划算。
为什么 role 用 user，不新增 role:'compaction'？ provider 的 message 只接受 user / assistant / toolResult，未知 role 会被拒。项目里已有成熟惯例：后台命令完成通知（details.quickforgeBackgroundCommand）、goal 续跑（metadata.quickforgeGoalRun）都是 role:'user' + details 标记，界面再按标记换渲染。压缩摘要的 details 契约已经存在：details.quickforgeCompaction = { version:1, kind:'summary'|'notice' }，手动 /compact 建新会话时就在用。
04

方案 B 契约

照着这份契约实现，位置问题在结构上就不可能出现。

4.1 消息形状

{
  role: 'user',                       // provider 兼容 + 与既有惯例一致
  content: [{ type: 'text', text }],   // 'The previous conversation has been compacted…' + <compact_summary>…</compact_summary>
  timestamp: Date.now(),                 // 仅用于排序/展示，不再参与定位
  details: {
    quickforgeCompaction: {
      version: 1,
      kind: 'summary',                   // 已有契约：'summary' | 'notice'
      compactedAt,                       // 本次压缩时刻（tooltip 用）
      keepRecentTurns,                   // 本次保留的回合数（诊断）
      sourceMessageCount,                // 被摘要的消息条数（诊断）
      usageBefore, thresholdPercent,     // 用量快照（诊断）
      mergedIntoLater?: true             // 之后又压过 ⇒ pill 追加「已并入后续摘要」
    }
  }
}

摘要正文仍是现在这段带 <compact_summary> 标签的文本：模型侧语义不变，只是它现在同时是「消息」。

4.2 插入点与时序

自动压缩触发（阈值 + 有新消息），与现在完全一致。
生成摘要（一次 LLM 调用）；失败则什么都不写：不插消息、不改状态（原子性）。
在 tailStart 处插入压缩消息（= 被摘要范围的右边界，即当前回合第一条用户消息之前）。插入后数组顺序就是最终阅读顺序：被摘要历史 → 压缩点 → 保留回合 → 之后产生的一切。
持久化：中间插入不能走 append，走 messagesMode:'replace' 全量写入（压缩本来就要写一次备份 saveCompactBackup，成本已有）。
投递：发 messages_replaced 帧（全窗口替换），客户端 applyLog(replace) 重建；多端靠 messageLogVersion 对齐。这是压缩现有行为，不新增通道。
模型上下文：下一次 transformContext 直接 messages.slice(indexOfLastCompaction)，不再读 compactedUpToIndex。

4.3 模型上下文投影（前后对比）

现在 用外部下标切片，且 summary 是「凭空加进来的第一条」

function buildAutoCompactLoopMessages(session, messages) {
  const s = session.contextCompaction.summaryMessage
  if (!s) return messages
  const cut = clamp(session.contextCompaction.compactedUpToIndex, …)
  // 跳过开头的孤儿 toolResult…
  return [s, ...messages.slice(cut)]     // ← 两份真相拼接
}

方案 B 消息数组本身就是上下文，压缩点是切片起点

function buildCompactedContext(messages) {
  const i = lastIndexWhere(messages, isCompactionMessage)
  return i < 0 ? messages : messages.slice(i)  // 单源切片
}
// messages 中已含 summary 消息本身，
// 「界面顺序 == 模型顺序」自动成立。

4.4 渲染契约

  • 一个组件一条消息：CompactionMessage 渲染「横线 + pill +（折叠的）摘要卡」，取代现在由 MessageList 往消息之间插节点 + 独立 ContextCompactionNotice 的做法。
  • 默认折叠：pill 一行（已压缩上下文 · 保留 N 回合 · 摘要），点开是摘要正文 + 复制按钮（1200ms 反馈保留）。摘要可能很长，正文用 pre 且展开时才渲染，符合渲染内存约束。
  • 滚动与定位：它是一行普通消息，滚动锚定、窗口分页、data-message-index、渲染 key 全部沿用现有逻辑，没有额外分支。
  • 装饰层跳过：不能被当成用户气泡 —— 不加编辑/回滚/重试/输入折叠/上下文 chip，只保留「复制摘要」。判定沿用 goal-internal 那条既有通道（details.quickforgeCompaction ⇒ 移除动作行并 return）。
  • 多线：连续压缩产生多条压缩消息，各自独立折叠；非最新一条 pill 追加「已并入后续摘要」（与现在 history 的语义一致）。

4.5 回滚 / 重试 / 分叉 / 分享 / 多端

场景现在（两份真相）方案 B（消息是真相）
回滚截断后比较 rollbackIndex < compactedUpToIndex 决定是否整块 resetSessionCompaction；坐标不重算。截断把压缩消息一起删掉 ⇒ 压缩自然失效，无需比较；保留则仍然生效。
重试同一逻辑的第二份实现（lastUserIndex 比较）。同一套切片语义，没有第二处判断。
分叉前端只复制 messages，不复制 contextCompaction ⇒ 分叉后「历史显示完整、压缩状态丢失」。压缩消息随 messages 一起复制 ⇒ 分叉后仍压缩、仍有线、位置仍正确。
分享 / 只读摘要靠 sanitizeContextCompaction 单独脱敏。摘要就是消息，走 sanitizeMessage；分享页的线与主端一致（只读、无按钮）。
多端一致压缩状态靠事件白名单字段带过去，可能落后于消息。压缩点就是消息，双游标投影天然一致；断线重连只需补齐消息。
恢复 / 重开空 contextCompaction ⇒ 线消失。消息在 = 线在，与进程/重启无关。

4.6 连续压缩、合并与失效

  • 多次压缩：每次都插一条新的压缩消息，模型从最后一条开始读。前面的压缩消息留在消息流里（历史可读），pill 标「已并入后续摘要」。
  • 切点选择：~~沿用现有 resolveAutoCompactTailStart（自动路径保底保留当前用户回合）~~ 已修订：切点固定为压缩发生那一刻的数组末尾，自动/手动同语义；当前用户请求由摘要承载，不再保留尾部回合。
  • 失效：回滚到压缩消息之前 ⇒ 消息没了 ⇒ 下一次请求读到完整历史，压缩「自动解除」，不需要额外 reset。
  • 清理：不清理历史压缩消息（它们是时间线）。数量上限沿用现在 history 的 20 条思路；把同一回合内的多次压缩聚合为一行是独立迭代，不在本期。
05

交互演示

同一段对话、同一批操作，只切换「位置怎么来」。请依次点：① 触发压缩 → ② 继续执行 tool → ① 再压缩 → ③ 回滚 → ④ 窗口滑动。

位置是怎么得到的

演示里被点名的三件事

  • 压缩那一刻线在底部：现状把「当时的数组长度」当位置，那就是末尾；方案 B 把它插在当前回合之前，线下立刻是本回合。
  • 线压住了没被摘要的行：现状压缩时本轮已跑完的 tool 在数组里，于是它们全在线之上，但摘要并不包含它们；方案 B 这些行在压缩点之后，天生在线下。
  • 窗口一动就漂：现状 recorded 落在窗口外只能 clamp（位置变成假的）；方案 B 的消息不在窗口内就不渲染，不会假装在别处。

演示刻意省略的部分

真实实现里还有：摘要生成耗时的「整理中…」行（沿用 ContextCompactionStatusRow）、要求确认时的审批行、附件与多模态、messageLogVersion 的增量补洞。它们在方案 B 下都不变，所以演示不重复。

06

时序：一次压缩从触发到上屏

run 中途：transformContext 发现超阈值 → 发布 compactionNotice(summarizing)（界面出现「整理上下文…」行，位置在列表尾部，不变）。
摘要返回：服务端构造 compactionMessage，saveCompactBackup() 存原文，messages.splice(tailStart, 0, msg)。
持久化：saveInTransaction({ messagesMode:'replace' })；messageLogVersion + 1。
广播：messages_replaced（含完整 messages 与 logVersion）→ 所有连接 applyLog(replace)。
渲染：消息流里出现一条 CompactionMessage，位置 = 它的下标；后续 tool / 回答继续 append 在它后面。
下一次模型调用：messages.slice(lastCompactionIndex) 作为上下文；模型看到的第一条就是摘要消息。

验收清单

行为断言（可直接写成测试）

  • 压缩消息的 index 等于 tailStart，且它是数组里 role==='user' && details.quickforgeCompaction?.kind==='summary' 的最后一条。
  • 插入后 messages.length +1；插入点之后的消息内容与顺序完全不变（纯插入，不是重建）。
  • 压缩后继续产生的 toolResult / assistant 行，其下标都大于压缩消息下标。
  • 回滚到压缩消息之前的消息 ⇒ 数组中不再有压缩消息 ⇒ 下一次请求上下文等于完整历史。
  • 连续压缩两次 ⇒ 两条压缩消息，模型从第二条开始切片；第一条 pill 标「已并入后续摘要」。
  • 窗口滑动 / 分页 / 切回合导航后，压缩消息位置只随其真实下标变化；不在窗口内则不渲染（不 clamp 到边缘）。
  • 摘要生成失败 ⇒ 消息数组与 messageLogVersion 都不变。
  • 分享页与主端看到同一条线、同一段折叠摘要；只读无按钮。

人工验收（实机）

  • 长会话里连续触发 3 次自动压缩：每条线都停在其发生处，线上方没有任何「本轮还在跑」的 tool。
  • 压缩正在发生（几十秒）时有「整理上下文…」，且不出现「线先冒出来、内容后补上」的错位。
  • 压缩后立刻刷新页面 / 换设备打开：线位置一致。
  • 回滚到压缩前再继续对话：线消失且模型回到完整历史。
09

风险与取舍

中间插入的代价

splice 是 O(n)（n = 消息条数，通常百级），持久化走一次全量 replace，投递一次全窗口替换帧。压缩本身是秒级 LLM 调用，这些开销不改变量级；换来的是「没有坐标可漂」。

窗口外的压缩点

旧方案必须 clamp 到边缘（否则线会消失）；方案 B 允许它自然不渲染 —— 因为它确实不在可见区间里。上翻到那里时消息自然出现。

与 provider 的兼容

一条 role:'user' 的摘要消息在上下文最前面，与现在 buildAutoCompactLoopMessages 的产出结构一致，provider 侧无新风险；isUserMessage() 已排除 summary 消息，不会污染「最后一条用户消息」判定。

需要留意的边角

  • fork 的 hasUserMessage 校验用 isUserMessage：分叉点若只落在压缩消息位置需要放行。
  • 分享脱敏：摘要正文可能含敏感信息，沿用 sanitizeMessage，必要时对摘要单独 redact。
  • 压缩消息不应参与 AI 标题生成的输入（手动 /summary 目前会把它算进去）。
  • 渲染内存：摘要正文只在展开时渲染，折叠态仍要把文本留在消息对象里（data-summary-text 现有做法可保留）。
结论：把压缩摘要做成消息，不是「换一种表达」，而是把位置的责任交还给唯一有资格持有它的东西 —— 消息序列。定位代码（换算、clamp、时间戳扫描、双信号取 min）可以整段删掉；回滚 / 分叉 / 分享 / 多端不再有「压缩特例」。这也是为什么它比继续修坐标更省：越少的知识，越不会出错。
