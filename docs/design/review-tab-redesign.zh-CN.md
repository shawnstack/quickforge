# 右侧「审阅」Tab 改版设计方案 V2

> 状态：已完成 subagent team 调研与独立 UI Review，可在确认关键产品语义后进入实现
> 范围：右侧 Workspace Inspector 中的 `Review → Changes` 视图
> 输入：用户提供的宽、窄两种截图；QuickForge 当前源码；`DESIGN_LANGUAGE.md`；Explore、UI Auditor、PM 与 UI Review Auditor 的结果

## 1. 设计结论

推荐将当前审阅界面改为一个以“范围摘要—文件识别—审阅操作”为主线的响应式工作区：

1. 顶部工具栏优先保留 **当前范围、文件数量、可置信的增删摘要、刷新**；只有存在至少两个明确低频动作时才显示“更多”。
2. 文件行采用 **文件名为主、父路径为辅**，不在宽栏长期平铺完整路径，也不在窄栏只依赖省略号和原生 `title`。
3. 单文件操作按空间逐级折叠：宽栏与中栏的主操作常驻但弱化，窄栏常驻“更多”，不能以“先选中文件”为动作出现条件。
4. 将底部悬浮胶囊改为 **稳定的 sticky footer**，只突出当前视图的安全主操作；批量丢弃进入“更多”或 tertiary 入口。
5. 所有布局根据审阅容器实际宽度响应，不使用 viewport 断点。
6. 数据语义是 UI 上线前置条件：批量作用域、增删统计口径、部分暂存与未跟踪文件的丢弃语义必须先与服务端行为一致。
7. 340–399px 打开 Diff 时切换为 **全宽 Diff 详情**，文件列表收为可返回的抽屉/上一级视图，不在窄宽度内硬挤左右分栏。
8. Review 文件列表建议保持至少 280px；140–279px 只作为临时极简导航，不承载完整审阅能力。

可视化方案见：[review-tab-redesign.svg](./review-tab-redesign.svg)。

## 2. 现状与关键问题

### 2.1 当前实现定位

```text
src/App.tsx
  → src/components/workspace/WorkspaceInspector.tsx
    → src/components/workspace/WorkspaceChangesList.tsx
      → src/components/workspace/WorkspaceInlineDiffPreview.tsx
```

相关接口位于：

- `src/components/workspace/workspace-api.ts`
- `server/routes/workspace.mjs`
- `src/components/workspace/workspace-types.ts`

### 2.2 当前界面问题

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 没有基于容器宽度的响应式机制 | 面板可拖拽、可全屏、可内部左右分栏，仅靠 viewport 无法正确适配 |
| P0 | 批量操作视觉作用域与后端真实作用域可能不一致 | 用户可能以为只处理当前筛选文件，实际处理整个仓库 |
| P0 | `还原全部` 与安全操作同权重 | 该操作不可撤销，且当前后端可能删除未跟踪文件 |
| P1 | 顶部工具图标过密 | 当前范围、摘要信息与低频工具争抢空间，图标语义依赖猜测 |
| P1 | 文件路径策略两极化 | 完整路径影响扫描；只显示 basename 又无法区分同名文件 |
| P1 | 三个行操作长期占位 | 即使视觉弱化，仍持续压缩文件名和统计 |
| P1 | 窄栏能力通过“消失”解决 | 总统计、批量操作隐藏后缺乏替代入口 |
| P2 | hover、选中、focus 区分不够完整 | 键盘用户与触屏用户不容易发现操作 |

### 2.3 当前实现与参考截图的差异

当前源码中：

- 普通右栏宽度为 340–640px；更宽的画面接近全屏状态。
- 所有宽度均只显示 basename，不存在“宽栏完整路径、窄栏文件名”的切换。
- 底部批量操作在所有宽度都会渲染，不存在窄栏自动隐藏逻辑。
- 当前顶部仅有筛选器和刷新按钮，参考图中的数量、总增删统计及多工具图标不是现有完整实现。

因此本方案不是简单样式微调，而是明确建立新的信息层级和响应式规则。

## 3. 设计目标与非目标

### 3.1 目标

用户打开审阅 Tab 后，应能快速完成：

1. 了解当前正在查看的变更范围。
2. 判断变更文件数量和代码改动规模。
3. 快速识别文件，尤其是同名文件。
4. 单击文件查看内联 Diff。
5. 暂存、退回或还原单个文件。
6. 在不离开面板的情况下完成批量操作。
7. 在 340px、380px、640px 和全屏状态下保持能力完整。

### 3.2 非目标

首版不建议引入：

- 文件多选复选框。
- Hunk/行级暂存与还原。
- 冲突解决器。
- Git Graph、Commit、Push 改版。
- 目录分组与复杂树形结构。
- 自动刷新文件系统监听。

搜索和排序有价值，但建议作为第二阶段；首版先解决布局、信息语义和危险操作。

## 4. 推荐信息架构

```text
Workspace Inspector Tab 栏
└─ 审阅工具栏
   ├─ 当前筛选：未暂存 / 已暂存 / 全部变更 / 上一轮更改
   ├─ 当前范围文件数
   ├─ 当前范围增删摘要（仅在口径精确时展示）
   ├─ 刷新
   └─ 更多（仅在存在明确低频动作时出现）
└─ 文件变更列表
   ├─ 文件类型图标
   ├─ 文件名
   ├─ 父路径 / 最短可区分路径
   ├─ Git 特殊状态
   ├─ 增删统计
   ├─ 当前视图主操作
   └─ 更多操作
└─ 内联 Diff
└─ Sticky 批量操作栏
```

### 4.1 顶部工具栏

推荐结构：

```text
[未暂存 33 ▾]  [+577  −409]                       [刷新] [更多]
```

规则：

- 第二行常驻 icon-only 按钮最多两个。
- MVP 若只有刷新一个明确动作，则只显示刷新，不为了视觉对称创建空壳“更多”菜单。
- 搜索、排序进入后续阶段；届时再放入“更多”菜单，并使用“图标 + 文字”。
- 数量属于当前筛选范围。
- 增删统计必须是当前筛选的精确口径；如果服务端暂时无法提供，则 MVP 只显示范围和文件数，不展示近似摘要。
- 增删统计必须同时保留 `+`、`−`，不能仅靠红绿颜色。
- 340px、英文文案、四至五位文件数或增删数下空间不足时，降级顺序为：保留筛选与数量 → 保留刷新 → 将增删摘要收进可聚焦摘要入口；不得继续缩小正文字号。
- “全部分支更改”建议改名为“全部变更”，因为当前数据是工作区状态，并非跨分支数据。

### 4.2 文件行

宽栏推荐：

```text
[TS] WorkspaceChangesList.tsx                 +54  −12   [+] […]
     src/components/workspace
```

窄栏推荐：

```text
[TS] WorkspaceChangesList.tsx        +54 −12   […]
```

路径规则：

1. basename 是主信息。
2. 宽栏显示弱化父路径。
3. 中栏仅在同名文件存在时显示最短可区分父路径。
4. 窄栏优先显示 basename；同名文件采用中间省略的最短可区分路径，例如 `src/…/index.ts`。
5. 完整路径通过自定义 tooltip/popover 或更多菜单查看和复制，不能只依赖浏览器原生 `title`。
6. 重命名显示 `旧路径 → 新路径`，搜索需同时命中两者。

### 4.3 行操作优先级

1. 当前视图主操作：未暂存时为“暂存”，已暂存时为“退回未暂存”。
2. 打开新标签。
3. 丢弃 tracked 文件更改；未跟踪文件必须使用“删除未跟踪文件”。
4. 复制路径等低频操作。

显示规则：

- 宽栏：主操作与更多常驻，默认弱化，hover/focus-within 时强化。
- 中栏：主操作常驻；更多可常驻或在 hover/focus-within 时出现。
- 窄栏：更多常驻；主操作仅在空间验证通过时保留。
- 不能把“选中文件/展开 Diff”作为动作出现的唯一条件。
- 危险操作收入更多菜单末尾，并用分割线与普通动作隔开；默认不使用红色，只在 hover/focus 与确认语境中使用危险色。

### 4.4 批量操作

推荐将当前居中悬浮胶囊改为 sticky footer：

宽栏：

```text
[更多]                                         [暂存当前 33 个]
```

窄栏：

```text
[更多]                                              [暂存 33]
```

规则：

- footer 高度稳定，不遮挡列表或内联 Diff。
- 只突出当前视图的安全主操作，并包含实际可操作数量。
- 批量丢弃不与主操作左右对称：始终放入“更多”，或仅在宽栏以 tertiary 文字入口“丢弃更改…”呈现。
- 未跟踪文件涉及真实删除；批量菜单和确认弹窗必须明确说明是否删除未跟踪文件。
- 执行时显示“正在暂存 33 个文件…”等明确状态。
- “当前 33 个”只有在 paths 批量接口已经实现、UI 与后端作用域完全一致时才允许出现；否则必须写成“暂存工作区全部更改”。

## 5. 容器响应式规格

> 使用审阅列表容器的实际宽度判断。推荐 CSS container query；若现有构建链路不便采用，则使用 `ResizeObserver` 输出布局等级。不要使用 viewport media query。

| 容器宽度 | 模式 | 工具栏 | 文件路径 | 行操作 | Footer |
| --- | --- | --- | --- | --- | --- |
| `≥ 520px` | 宽栏 | 筛选+数量、精确摘要、刷新；按需更多 | 文件名 + 父路径两层 | 主操作 + 更多常驻、默认弱化 | 更多 + 主批量操作 |
| `400–519px` | 中栏 | 筛选+数量、紧凑精确摘要、刷新；按需更多 | 文件名；同名时补父路径 | 主操作常驻，更多常驻或 focus/hover 出现 | 更多 + 主批量操作 |
| `340–399px` | 窄栏 | 筛选+数量、可容纳时显示精确 `+/-`、刷新 | basename；同名时最短可区分路径 | 更多常驻；主操作按验证结果保留 | 更多 + 主批量操作 |
| `280–339px` | 极简导航 | 当前范围、数量、刷新/更多 | basename | 全部进入菜单 | 批量操作进入菜单 |
| `< 280px` | 不承载完整列表 | 显示“变更列表”入口 | 不展示完整审阅行 | 不展示 | 不展示 |

### 5.1 窄栏打开 Diff 的状态转换

在 340–399px 下，文件列表与 Diff 不做左右分栏。交互状态如下：

```text
变更列表 --点击文件--> 全宽 Diff 详情
全宽 Diff 详情 --返回/Escape--> 变更列表（恢复滚动位置）
```

- 全宽 Diff 顶部显示返回按钮、文件名、最短可区分路径和文件主操作。
- 进入 Diff 后隐藏列表 sticky footer，避免批量操作与单文件详情竞争。
- 文件列表以抽屉或上一级视图保留，不卸载筛选、滚动位置和当前文件上下文。
- 只有容器可同时满足“列表至少 280px + Diff 可读宽度”时，才允许左右分栏。

### 5.2 极窄分栏策略

当前内部导航宽度可低至 140px，但完整 Git 审阅不适合这一宽度。推荐：

- Review 变更导航的完整模式最小宽度为 280px。
- 280–339px 只提供极简导航；选择文件后进入全宽 Diff。
- 低于 280px 时折叠为“变更列表”抽屉入口，不渲染被强行压缩的完整文件行。

## 6. 视觉规格

### 6.1 尺寸

| 元素 | 推荐规格 |
| --- | --- |
| 审阅工具栏高度 | 44–48px |
| 筛选按钮高度 | 32px |
| 图标按钮实际点击区 | 桌面最低 32×32px；coarse pointer 模式建议 44×44px |
| 图标视觉尺寸 | 14–16px |
| 文件行高度 | 单行 40–44px；双层信息 48–52px |
| 文件图标 | 15–16px，继续复用现有 `FileIcon`，不新增彩色徽章容器 |
| 主文字 | 13–14px，medium |
| 父路径 | 11–12px，弱化色；需验证对比度 |
| 增删统计 | 11–12px monospace；使用主题 token，不照搬线框硬编码色 |
| Sticky footer | 48–52px |
| 行内操作实际点击区 | 最低 32×32px |
| 列表左右 padding | 8–12px |

### 6.2 状态

| 状态 | 视觉规则 |
| --- | --- |
| 默认 | 干净背景，文字与图标保持柔和 |
| Hover | 淡 `muted` 背景，不位移、不改变尺寸 |
| 选中/展开 | 比 hover 更明确的淡背景，可使用极轻阴影 |
| Focus | 清晰独立的焦点环，不依赖选中背景 |
| Pending | 对应动作 spinner；阻止重复提交 |
| Disabled | 降低透明度，并提供禁用原因 |
| Error | 尽量邻近文件行或操作区显示，不只依赖全局 Alert |

视觉原则必须继续遵循 `DESIGN_LANGUAGE.md`：轻盈、克制、统一分割线、危险色默认不常驻、避免重卡片和图标堆叠。

## 7. 交互流程

### 7.1 查看 Diff

1. 单击文件主区域打开 Diff。
2. `≥ 520px` 且空间足够时可继续使用内联/左右分栏 Diff；340–399px 时切换为全宽 Diff 详情。
3. 全宽详情提供返回按钮与 Escape 返回，恢复列表滚动位置。
4. 行主按钮提供 `aria-expanded`/`aria-current` 或等价状态，并关联对应详情。
5. 操作按钮区域与主点击区分离，避免点击暂存时误打开 Diff。
6. 切换筛选后，如果当前文件不在结果中，关闭 Diff；当前实现已具备基础清理行为。

### 7.2 单文件暂存/退回

1. 点击主操作。
2. 仅对应行显示 loading。
3. 成功后更新列表、数量和摘要，保持列表滚动位置。
4. 失败后保留文件并显示可理解的错误，可重试。

### 7.3 丢弃或删除单文件变更

入口文案必须随文件语义变化：

- tracked 文件：`丢弃更改…`
- 未跟踪文件：`删除未跟踪文件…`
- 部分暂存文件：若当前实现会恢复整个文件到 HEAD，入口与确认中必须明确说明“同时丢弃已暂存和未暂存修改”

确认弹窗必须说明：

- 完整路径。
- 实际影响 staged、unstaged 中的哪些部分。
- 是否会删除未跟踪文件或目录。
- 操作不可撤销。

不能用统一的“还原文件”掩盖不同的数据破坏语义。

### 7.4 批量操作

1. 按钮显示实际作用范围和实际可操作文件数，而不是简单使用当前列表长度。
2. 批量丢弃必须二次确认，并明确 staged/unstaged 与未跟踪文件影响。
3. 进行中阻止重复操作，但列表可继续阅读。
4. 完成后通过 `aria-live` 宣布结果并更新摘要。
5. UI 与后端作用域必须在同一个 MVP 中完成：
   - 若实现 paths 批量接口，可使用“暂存当前 33 个”；
   - 若仍使用全仓库接口，只能使用“暂存工作区全部更改”等明确文案。
6. `all` 与 `last` 筛选必须分别定义可操作集合；“上一轮更改”不能仅因列表过滤为若干 paths，就调用全仓库 all 操作。

## 8. 数据与语义要求

这是实现前必须解决的部分，不能只通过样式完成。

### 8.1 数量口径

“未暂存 33”应代表当前筛选实际展示的文件数，包括产品明确纳入该筛选的：

- unstaged
- untracked
- conflicted

不得直接使用一个口径不同的后端 count。

### 8.2 增删统计口径

当前后端文件级 `additions/deletions` 更接近 `HEAD → 工作区` 总体变化，不能严格代表纯未暂存或纯已暂存变化。

顶部摘要属于高置信信息，MVP 必须采用以下二选一规则：

1. 实现当前筛选的精确统计后展示；或
2. 暂时不展示摘要，只显示筛选与文件数。

不允许显示近似数字后仅靠 tooltip 解释。精确统计建议分别计算：

```text
未暂存：git diff --numstat
已暂存：git diff --cached --numstat
全部：git diff HEAD --numstat
```

“上一轮更改”还需限定 paths 后再汇总。

### 8.3 批量作用域

推荐产品方案：批量操作作用于 **当前筛选范围**，符合所见即所得。

当前 `stage-all`、`unstage-all`、`restore-all` 实际作用于整个仓库。因此批量作用域不是 Phase 2 优化，而是实现 sticky footer 与数量文案前的 MVP 门槛：

- **推荐**：新增 paths 批量接口，使操作匹配当前视图。
- **兼容现状**：保持全仓库操作，但按钮、pending 文案和确认弹窗全部明确写出“工作区全部”。

### 8.4 丢弃与删除语义

服务端当前丢弃逻辑可能同时影响 staged、unstaged，并可能删除未跟踪文件。MVP 前必须定义：

- tracked 文件是否只丢弃当前视图对应部分，还是整个文件回到 HEAD；
- 部分暂存文件的 staged 与 unstaged 如何处理；
- 未跟踪文件/目录使用“删除”而不是“还原”；
- 批量操作是否会执行清理未跟踪文件。

UI 标签、确认文案、测试与服务端命令必须保持一致。

## 9. 无障碍要求

1. 所有 icon-only 按钮必须有可访问名称和 tooltip。
2. 文件操作名称包含文件名，例如“暂存 src/App.tsx”。
3. 不能只通过红绿颜色表达增删，必须保留 `+`、`−`。
4. 隐藏行操作时使用 `focus-within` 同步显示，不能只依赖 hover。
5. 路径信息支持键盘 focus 与点击触发，不只依赖 `title`。
6. 菜单支持 Escape 关闭和方向键导航。
7. loading 区域使用 `aria-busy`；完成结果使用 `aria-live="polite"`。
8. 尊重 `prefers-reduced-motion`。

## 10. MVP 验收标准

### 布局

- 在 340px、380px、520px、640px 和全屏状态下不出现整体横向滚动。
- 340px 列表态始终可访问当前筛选、文件数、刷新、单文件操作和批量主操作；增删摘要只有在空间和精确口径同时满足时才常驻。
- 340px 打开文件后切换为全宽 Diff，提供返回/Escape，并恢复列表滚动位置。
- 顶部第二行常驻 icon-only 操作不超过两个；没有真实菜单项时不渲染“更多”。
- Footer 高度 48–52px，不遮挡文件列表和 Diff。
- 同名文件无需依赖 hover 即可区分。
- 使用英文、四至五位文件数/增删数、200% 缩放验证布局不溢出。
- 继续复用现有轻量 `FileIcon`，不新增高饱和彩色文件徽章。

### 操作

- 单文件暂存/退回期间仅对应行显示 loading。
- 操作成功后文件数、列表和精确摘要同步更新。
- tracked 文件的危险入口使用“丢弃更改…”，未跟踪文件使用“删除未跟踪文件…”。
- 危险操作必须确认，部分暂存与未跟踪文件影响描述完整。
- UI 标示的批量范围必须与后端实际操作范围一致。
- `unstaged`、`staged`、`all`、`last` 四种筛选的批量可操作集合均有测试覆盖。

### 可访问性

- 所有核心功能均可通过键盘到达。
- icon-only 按钮具有可访问名称。
- hover 隐藏动作在 focus-within 时同样可见。
- 文件行展开状态可被辅助技术识别。

## 12. 实现前需要确认的产品决策

1. **批量操作作用范围**：当前筛选结果，还是整个工作区？
   推荐：当前筛选结果。
2. **部分暂存文件的丢弃语义**：只丢弃当前视图部分，还是整个文件回到 HEAD？
   推荐：精确按视图处理；若暂时做不到，必须强提示。
3. **顶部增删统计是否要求精确对应筛选？**
   推荐：是，否则已暂存/未暂存视图容易误导。
4. **首版是否包含搜索与排序？**
   推荐：首版不阻塞，Phase 2 增加。
5. **窄栏打开 Diff 的方式是否采用全宽详情 + 返回？**
   推荐：是；340–399px 不做左右分栏。

## 13. 推荐默认决策

若进入实现，建议采用以下默认值：

- 批量操作作用于当前筛选结果，并在 UI 改版前先实现 paths 批量接口。
- 顶部统计精确对应当前筛选；无法精确计算时暂不展示。
- 未暂存视图的主操作为“暂存”；已暂存视图为“退回未暂存”。
- tracked 文件使用“丢弃更改…”，未跟踪文件使用“删除未跟踪文件…”，危险入口放入更多菜单。
- Footer 只突出安全主操作，不与批量丢弃对称展示。
- 宽栏、中栏主操作常驻但弱化；窄栏更多菜单常驻。
- 首版不增加复选框，不增加 Hunk 级操作。
- 搜索与排序放入下一阶段；没有真实低频动作时不显示顶部更多菜单。
- 340–399px 点击文件后进入全宽 Diff；完整 Review 列表最小宽度 280px，更窄时使用抽屉入口。
