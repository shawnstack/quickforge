# 一个主体、两只手：单 agent 跨项目派单

> 状态：**设计文档，未落地**。本文只给结构与判据，不描述已实现的代码路径。
> 前置阅读：[自进化回路：六环契约与三档影响半径](./self-evolution-loop.zh-CN.md)。本文不新造判据，只把那套六环具体化成「一个会自己派活的 agent」。
> 相关：[工作流编排](./workflow-orchestration.zh-CN.md)、[记忆体系](./memory-system.zh-CN.md)。

## 1. 一句话

**只有一个 agent。** 它常驻、它决定、它派活。干活的和验收的都是它临时叫来的 subagent，用完即弃，不常驻、不建档、不占会话列表。

砍掉的是「三个常驻角色」那套架构（总台/工人/裁决各一个会话、三套状态机）。留下的是一条：

```
                  ┌──────────────────────────────┐
                  │  主体（唯一常驻的那个）        │
                  │  读信号 / 决定 / 派单 / 记账   │
                  └───────────┬──────────────────┘
                              │
              ┌───────────────┴───────────────┐
              ↓                               ↓
     ┌─────────────────┐            ┌─────────────────┐
     │ 手 A：干活        │            │ 手 B：验收        │
     │ 目标项目 · 全权限 │            │ 目标项目 · 只读   │
     │ 一次性            │            │ 一次性            │
     └─────────────────┘            └─────────────────┘
```

## 2. 为什么这仍然守住了「验证不能自己批」

既有文档 C2 说：**不能让同一个上下文既产出候选、又裁决候选**。

这条约束说的是「上下文」，不是「进程数」。所以：

- 干活的是手 A（一个 subagent，不知道主体在想什么）；
- 验收的是手 B（另一个 subagent，看不到手 A 的推理过程，只拿到代码 + 派单时写死的验收标准）；
- 主体自己不写 verdict，只把 B 的结论原文抄进账本。

**三个上下文，一个意志。** 这跟「三个常驻角色」在隔离强度上是等价的，成本却低一个数量级——因为 subagent 是一次性的，不需要持久化状态机、不需要各自的心跳、不需要三个会话。

如果连 subagent 都不想用（即主体自己干、自己判），那就是主动放弃 C2，需要在文档里明说，不能装作还在守。

## 3. 主体每次醒来做三件事

主体就是那条常驻任务。它醒来的剧本从「查三样东西写一行正常」变成：

### 第一步：收尾

上一班派出去的手 A / 手 B 结束了没有？

- 结束了 → 读它们的结论，落进账本；
- 手 A 干完但还没验收 → 叫手 B；
- 手 B 判了通过 → 按半径处理（R0 直接生效 / R1 停在待审 diff）；
- 手 B 判了不通过 → 记一次失败，连续 2 次就停这个项目；
- 还没结束 → 记一笔「在跑」，不打扰它。

**这一步是整套设计的关键。** 它意味着主体不需要额外的结算定时器：**它的「下一班」就是收尾的触发器**。心跳这个机制第一次有了第二个用途——不只是「确认活着」，而是「收上一班的尾」。

### 第二步：扫描

跑一个纯脚本，算每个 workspace 的信号（§6）。**零 token，不管几个项目。**

### 第三步：派单

按分数挑项目，最多派 N 单（受预算约束）。每单必须写全四样（§7），缺一不派。

三步都没事 → 写一行「无信号」睡回去。这才是「不要为了有事干而制造工作」的正确实现。

## 4. 两只手怎么落地：都是现成的

| 手 | 用什么 | 为什么 |
| --- | --- | --- |
| 手 A 干活（跨项目） | `spawn --project <id>` → 在目标项目里起一个会话 | 它的 workspace、AGENTS.md、项目记忆自动切过去；`spawn` 默认就是 full-access，符合「全权」要求 |
| 手 A 干活（本项目内） | `run_subagent`（general profile） | 同一个 workspace，不用新会话 |
| 手 B 验收（本项目内） | `run_subagent`（`readonly-research` 能力策略） | **物理上改不了东西**，只能读和跑命令 |
| 手 B 验收（跨项目） | 缺能力，见下 | |

### 4.1 一个真实缺口：跨项目的验收没有只读通道

`run_subagent` 有 `readonly-research` 这种能力策略，能把工具收窄到只读。**但 `spawn` 出来的跨项目会话没有对应参数**——它只有 `--access-mode default|full-access`，而 `default` 的意思是「工具调用要审批」，在无人值守下会卡住（等 5 分钟审批超时），不是「只读」。

所以「派到别的项目去验收」目前只能二选一：

- 给手 B 也 full-access，靠 instruction 说「你只许读」——**靠自觉，不是物理约束**，弱；
- 或者补一个能力：给会话/spawn 加只读访问模式（工具白名单只有读类）。

**设计上必须补后者。** 它不新增架构，只是把 subagent 已有的能力策略接到 spawn 上；不补的话，跨项目验收就退化成「一个全权子会话答应只看」。

## 5. 账本：一张纸，不是第二个人

「只有一个人」不等于「不留痕」。必须有一份最小的派单记录，否则派出去的东西会消失——这是这套设计里唯一不可省的结构。

每单一行，落在 `logs/orchestrator/dispatches.json`（`logs/` 已在 `.gitignore`）：

```json
{
  "id": "d-20261111-0820-1",
  "projectId": "...",
  "projectName": "noteflow",
  "title": "修掉 note 列表分页越界",
  "objective": "翻到最后一页不再报错",
  "acceptance": "npx vitest run tests/note/pagination -> 0 failed",
  "boundary": ["src/note/", "tests/note/"],
  "radius": "R1",
  "reason": { "dirty_files": 4, "handoff_open": 1, "score": 5 },
  "status": "verifying",
  "workerSessionId": "scheduled-...",
  "verifierSessionId": "...",
  "verdict": null,
  "attempts": 1,
  "createdAt": "...", "finishedAt": null
}
```

为什么用 JSON 不建 SQLite 表：一个人的调度状态不需要事务和联表查询，一个文件读写就够，出问题人能直接打开看。真要做 UI 时再升表也不迟——**但不要为了将来可能有的 UI 先建表**。

这份账本的第二个用途：**它就是「怎么看每次心跳干了什么」的答案**。不用一条条点开会话，一张表把「哪次醒 → 看见了什么信号 → 派了什么活 → 判成没成 → 会话链接」串起来了。

## 6. 信号：每个 workspace 一行，零 token

| 字段 | 怎么算 | 说明 |
| --- | --- | --- |
| `dirty_files` | `git status --porcelain` 行数 | 有多少改动没收尾 |
| `dirty_age_hours` | 最老的未提交文件 mtime | 拖了多久 |
| `days_since_commit` | `git log -1 --format=%ct` | 项目停摆没有 |
| `handoff_open` | `session-handoff.md` 里「下一步/未完成/blocker」条数 | 人写好但没做的事 |
| `feature_pending` | `feature_list.json` 里非 done 且依赖满足 | 计划内的活 |
| `last_verdict` | 上一单验收结果 | 红不红 |
| `stuck_sessions` | 该项目下 `status=running` 且 >2h 无活动 | 有没有卡死的活 |

打分（≥3 才算「有活」）：

```
+3   dirty_files > 0 且 dirty_age_hours > 24
+3   stuck_sessions > 0
+2   handoff_open > 0
+2   feature_pending > 0
+2   last_verdict = failed
+1   days_since_commit > 7
```

写死在代码里，不交给模型。理由是：让模型每班「感觉一下哪个项目有事」既贵又不稳定，而这恰恰是唯一能零成本做对的部分。

## 7. 派单契约：四样写不全就不派

| 字段 | 要求 | 会被拒的例子 |
| --- | --- | --- |
| `objective` | 一句话说清要达成什么 | 「优化一下测试」 |
| `acceptance` | 可执行判据：命令 + 期望 | 「跑通就行」 |
| `boundary` | 允许改的路径白名单 | 「随便改」 |
| `radius` | R0 / R1 / R2，且与 boundary 一致 | 说是 R1 却把整个仓库列进 boundary |

这条是枢纽：**它把「目标」从散文变成了可判定的东西。** 写不出验收的活，说明还没想清楚，留在账本里等人，别派。

## 8. 准入：按半径，不按对错

| 半径 | 手 A 在哪干 | 手 B 判过之后 |
| --- | --- | --- |
| **R0** 自留地（报告、笔记、审查清单） | 直接写数据目录 | 自动生效，自带整轮快照 |
| **R1** 工作区（源码、测试、文档） | **独立 worktree** | 停在「待审 diff」，等人放行 |
| **R2** 内核（提示词、记忆格式、工具白名单、权限默认值） | — | **派单前就拒**，连账本都进不去 |

R1 用 worktree 不用 stash：对比和整批丢弃都是单条命令，且不碰主工作区的 git 状态。

## 9. 全权限怎么给，以及唯一不放开的那条

用户明确要全权。所以手 A 是 full-access，主体也是 full-access——**不给权限设审批关卡**。

放开的理由：这个人已经决定要它自己干，加审批只会让无人值守变成「等人」。

但有一条不放开，而且不是权限问题，是产品规矩：**任何半径下都不自动 `git commit / tag / push`。** R1 的产出止于待审 diff。这条不是限制 agent 的能力，是保护人的复核权——一旦自动提交，出错的成本从「丢一个 worktree」变成「污染历史」。

## 10. 预算与熔断

不是审批，是资源边界：

| 项 | 默认 |
| --- | --- |
| 每次醒来最多派 | 2 单 |
| 同项目并发 | 1 |
| 每天最多派 | 6 单 |
| 单工单最长 | 30 min |
| 连续验收失败 | 2 次 → 该项目暂停派单，等人 |

**熔断**（命中即 abort 全部子会话 + 主体进入 paused + 写高优先报告）：

- 任何单试图 commit / push / tag
- 任何单碰 `dist/`、`package-dist/`、`package-offline/`
- 任何单改到 R2 清单里的东西
- 同一单连续 3 次失败

## 11. UI

主体不属于任何项目，所以不能挂在某个 workspace 下面。放在**侧栏顶部**（与设置入口并列），一个图标带状态点：

- 绿 = 闲；蓝 = 有单在跑；黄 = 有待审 diff；红 = 熔断/暂停

点开是两栏：

- **左**：workspace 列表（就是主页面左边那些项目），每行显示信号灯 + 分数 + 手上的单数。一眼看出谁有事。
- **右**：账本流，一行一单。点开是详情：目标、边界、验收、手 A / 手 B 的会话链接、判定原文、diff、放行/拒绝。

## 12. 与既有契约的关系（明账）

| 既有条款 | 本文 |
| --- | --- |
| C2 验证者与生成者隔离 | **遵守**，用两个一次性 subagent 实现（§2） |
| R2 内核不自动化 | **遵守**，派单前拒 |
| 不自动 commit / push / tag | **遵守**，明文写进熔断 |
| R1「自动产出，人审入库」 | **遵守**，停在待审 diff |
| 「不为自进化放宽审批边界」 | **取舍**：用户明确要全权，v1 的 spawn 默认就是 full-access，既有文档 §8.3 已承认这是已知取舍。不放宽的是 commit 那条 |
| 「优化顺序从后往前」 | **遵守**，见 §13 |

## 13. 实施顺序（依赖链，不是缩水）

完整图景就是 §2–§11。但顺序不能跳，理由不在成本：

| 阶段 | 内容 | 判据 |
| --- | --- | --- |
| **0** | 清掉既有文档 §8.3 三处「描述与实际行为不一致」 | 手 B 读到的状态必须是干净的 |
| **1** | 信号脚本 + `qf-api signals`（零 token） | 能一眼看见 5 个项目谁有事，不花一分钱 |
| **2** | 主体会派单：账本 + 四样校验 + `spawn --project` | 派出去的单有边界和验收 |
| **3** | 主体会收尾：读子会话状态、回写账本 | 派出去的东西不会消失 |
| **4** | 手 B 隔离：给 spawn 补只读能力（§4.1） | 跨项目验收有物理约束 |
| **5** | 准入与回滚：worktree + 放行/拒绝 | R1 出错能整批丢弃 |
| **6** | 替换现有每小时心跳的 instruction | 从「查三样写一行」变成「收尾/扫描/派单」 |
| **7** | UI：侧栏入口 + 项目信号灯 + 账本流 | 依赖 1–5 的数据 |
| **8** | wiki / endpoints / 契约测试同步 | 按项目规矩 |

阶段 1 独立可验证、零风险，做完立刻有用。阶段 4 是整套设计能不能守住 C2 的分水岭。

## 14. 不做

- 不自动 commit / tag / push。
- 不改 R2 内核。
- 不建第二个常驻角色、不建 SQLite 工单表（先用一个 JSON 文件）。
- 不让主体自己裁决自己派的活。
- 不为派单新增依赖。
- 不把「每班扫一遍所有项目」当覆盖度——信号驱动，没事就睡。

## 15. 开放问题

1. **总台住哪。** 主体 `projectId` 为空时，执行 cwd 会 fallback 到默认 workspace（`server/project-config.mjs:416-425`），不是「没有目录」。设计上让它的状态只落 `logs/orchestrator/`，不改任何项目仓库。
2. **「该不该派」仍无人判定。** 信号能说「有改动没收尾」，说不了「这件事值不值得做」。这是既有文档 §8.1 的缺口，本文没解决。
3. **subagent 的成本。** 每单至少两跳（干活 + 验收）。所以阈值要保守：宁可少派。
4. **跨项目工单归属。** 一张「让 A 和 B 对齐接口」的单该挂谁名下？当前 `projectId` 单选，只能挂主项目，是已知的粗糙处。
