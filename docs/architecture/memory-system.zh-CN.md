# 记忆体系：工作记忆 + 经验库

> 本文取代 [`dreaming-memory.zh-CN.md`](./dreaming-memory.zh-CN.md)。旧文描述的是「一次 LLM 调用把会话压成 `DREAMING.md` 里一份 bullet 列表」，那套机制已经整体退役。

## 1. 要解决什么

会话里学到的东西，需要一个地方留下来。难点不在「记」，在「三年后还读得懂」：

- 记在会话里 → 开新会话就没了。
- 记在一个越来越长的文件里 → 最后没人（也没有模型）愿意从头读完。
- 记成一份必须手写的知识库 → 没人维护，三个月后全是过期条目。

所以这里没有「一份大记忆」，只有三层分工不同的小仓库。

## 2. 三层结构

```
MEMORY.md                   用户的偏好（"用大白话讲"）        注入全文，极小
working-memory/             活笔记：这件事现在是什么样        只注入路径+写法
experiences/                经验：以后遇到同类问题怎么做       只注入 index.md
  └ index.md                                             （扫描生成，200 行封顶）
skills/                     能力：改变 AI 做事方式            人工确认才建
```

三层的淘汰规则不一样，这是整个设计的核心：

| 层 | 谁写 | 要不要人审 | 生命周期 |
| --- | --- | --- | --- |
| `MEMORY.md` | 用户（+ `manage_global_memory` 代笔，只写不读） | 是 | 长期，手工维护 |
| `working-memory/` | 会话中的 AI、梦境整理员 | 否 | 短，过期就改或归档 |
| `experiences/` | 梦境整理员 | 否 | 长，只增不删 |
| `skills/` | 人 | 是 | 由经验升级而来 |

**为什么经验不需要人审、技能却需要**：经验是纯文本资料，写坏了读一遍就能发现，而且有快照可以整轮回滚；技能会改变 AI 的行为方式（它会被自动加载进系统提示词），所以必须由人点头。这条边界是硬的，不靠提示词自觉——整理员根本没有碰 `skills/` 的工具。

## 3. 文件格式

两个目录共用同一套规则，代码在 `server/note-store.mjs`：

- 一个文件一件事。
- **文件名就是结论那句话**，正文第一行 `# 标题` 必须和文件名一致。
- 不超过 4000 字符。
- **没有删除功能**。退休一篇笔记 = 用 `move_memory_note` 挪进 `_archive/`。归档是可逆的，删除不是。

工作记忆是随手记，格式宽松；经验是给几个月后看的：文件头是给程序读的 front matter，正文只剩读的人需要的几段。

```markdown
---
title: 构建失败先清 dist 再重新跑
description: npm run build 报奇怪的 chunk 错或产物和源码对不上时
general: true
candidate_skill: false
---

- 怎么做：删掉 dist/ 再跑一次
- 坑：chunk 超 500kB 和 module.register() 弃用提示都是无害警告
- 来源：工作记忆「构建产物诡异.md」，11-02 / 11-04 出现过 3 次
```

- `title` 必须和文件名逐字相同，写入时校验，不一致直接拒绝；要改结论就用 `move_memory_note` 改名，不要原地改标题。改名会顺手把 front matter 的 `title` 一起改写（只改这一行，含 ` #` 之类的值会自动加引号），所以「先改名、再更新内容」是连续可用的两步；返回值里的 `titleSynced` 报告这次有没有改写（`null` = 本来就没有或不用改）。
- `description` 取代了旧的「何时用」bullet，只给设置页和打开文件的人看，不进索引。
- `general` 只有一个问题：换个项目能不能照着做？正文里出现本项目的文件名、路径、命令、符号或产品行为，答案就是 `false`。判据是「读到哪句会停下来问『哪个文件？』」——那一句就是特殊的地方。缺省算 `true`，所以索引里只给 `false` 的加标记。
- `candidate_skill` 表示「够格升级成技能」，并且**必须 `general` 也是 `true`**：技能会被加载进所有项目，把一条特殊经验升成技能，等于把一个项目的细节写成所有人的默认行为。两处强制：写入时直接拒绝这种组合（`writeExperience`，和 title 不一致同样处理），读取时 `experienceMetaOf` 再做一次与运算兜底——后者是给手改过的文件留的，不是正常路径。
- 值是中文也能读：`general: 否` / `是`、`no` / `yes` 都认。共用的 `firstOptionalBoolean` 只认 `true` / `false`，而这批笔记是中文写手写的，`否` 被当成「没填」再回落到默认 `true`，正好是这条轴要防的静默错误，所以在经验这一层单独解析。

旧格式（`# 标题` 加 `- 何时用：` / `- 候选技能：` bullet）仍然能读：`noteHeadingOf` / `noteWhenToUseOf` 先看 front matter，再回退到 bullet。所以不存在「必须一次性迁移完」的窗口。

## 4. 索引是生成的，不是维护的

`experiences/index.md` 每次读取时由代码扫描目录重建，一条一行，**只放文件名**：

```markdown
- 改全局记忆前先备份（特殊）
- ★ 构建失败先清 dist 再重新跑
```

`—— 何时用` 那半截去掉了：文件名本来就是结论句，再把 `description` 抄一遍等于为同一句话付两次钱。唯一值得多花几个字的是 `（特殊）`，因为它是「别照着做」的唯一信号。

这么做的原因很实际：索引是**每一条消息都在付钱**的东西（它在系统提示词里），一旦允许手工维护，就一定会和实际文件不一致，而且是往「多出一条不存在的经验」的方向不一致。生成式索引只有一个真相来源——目录本身。

上限 200 行 / 20000 字符。按最宽的一行算（★ + 60 字标题 + `（特殊）`），200 行仍在一万四千字符以内，所以现在先撞到的是行数上限，不是字符上限。超出的旧条目掉出索引但文件还在，这是有意设计的失败模式：索引是指针，不是副本。

## 5. 注入策略：渐进式披露

系统提示词里放什么，决定了每个会话的固定成本：

```
<memory>          MEMORY.md 全文
<experiences>     目录路径 + index.md 全文 + "这只是提示，要看就自己读"
<working_memory>  目录路径 + 写法规则（不注入内容）
```

关键在最后那条说明。只给索引会带来一个具体的失败模式：模型拿着索引那一句话当结论，开始编细节。所以注入块里明确写着「Before relying on an entry, open that one file」；反过来也要写「If nothing in the index looks relevant, do not go browsing」——否则模型会为了显得勤奋而翻遍目录。

索引行尾的 `（特殊）` 也在注入块里解释了一句：这条流程的形状成立，但里面的文件名、路径、命令属于那个项目，用之前要换成本项目的。没有这句，模型会把 `（特殊）` 当成一个它不认识的花纹。

工作记忆不注入内容的理由不同：它的量没有上界，而且大多数会话根本不需要。列一次目录是毫秒级的事，比每轮都背着它便宜。

## 6. 四个工具

文件夹在 workspace 之外，所以给 AI 的是四个路径锁死在这两个目录里的工具，而不是 `run_command`：

| 工具 | 参数 | 用途 |
| --- | --- | --- |
| `list_memory_notes` | `scope` | 列目录，看已有什么 |
| `read_memory_note` | `scope`, `name` | 读全文 |
| `write_memory_note` | `scope`, `name`, `content` | 新建或覆盖 |
| `move_memory_note` | `scope`, `from`, `to` | 改名，或 `_archive/<name>` 归档 |

`scope` 取 `working` 或 `experience`。

**为什么不用 `run_command`**：梦境整理员是无人值守跑的，弹不出审批框；给它 shell 等于给它整个磁盘。这四个工具能做到「只能碰这两个目录」是工具列表保证的，不是提示词保证的。会话里的主 AI 用同一套工具，人和机走一条路，行为才一致。

`write_memory_note` 拒绝空正文——「写空 = 删除」是这一层唯一不提供的破坏性操作，否则一次被截断的模型回复就能抹掉一篇笔记。

### 谁能拿到哪几个

| 调用方 | 拿到什么 |
| --- | --- |
| 会话主 AI | 四个全给（`createServerTools` 无条件挂载，再按 `allowedToolNames` 过滤） |
| 梦境整理员 | 自己单独建工具集，四个全给 |
| subagent / 自定义 Agent Profile | 只有 `list_memory_notes` 和 `read_memory_note`（`MEMORY_READ_TOOL_NAMES`），且五条能力策略都允许 |

subagent 只给读：它短命且可能并行，几个 subagent 各自判断「这条值得记」，就会往同一个工作记忆里塞重复笔记，而收尾沉淀本来就归父会话。反过来，读是必须给的——父会话的 system prompt 整段透传给 subagent，那份索引它已经看见了；不给工具只会让它绕 `run_command` 去 `cat` 绝对路径，那条路要人点审批，无人值守时就卡到超时。这两个工具同时在 `safeReadTools` 里，所以 subagent 读笔记不弹框。

`write_memory_note` / `move_memory_note` 不在 `AGENT_PROFILE_TOOL_NAMES` 里，因此不会出现在 Agent Profile 的可选工具列表，也进不了任何策略。

### 人怎么看到这些文件

设置页不提供编辑，但给了一个出口：工作记忆的每条笔记、经验库的每条经验后面都有「打开」，两个页面也各有「打开文件夹」——都在系统文件管理器里定位到那个 `.md` 文件 / 打开整个目录。

两端共用 `note-store.mjs` 的 `revealNoteFile()`：路径由服务端拼，名字过的是和写入同一套 `normalizeNoteName`，客户端只能传一个文件名。所以「打开」不会变成一个任意文件读取口子。目录在打开前会先建好（新装机器上目录还不存在时也能点）。

## 7. 梦境：一次一个会话的整理员

定时器和以前一样：默认每天 `executeTime`（默认 03:00）触发一次，窗口是「上次成功运行的 `period_to` 到现在」。

不同的是触发了以后干什么：

```
1. 取窗口内的会话（全部，串行，按时间从旧到新）
2. 把 working-memory/ 和 experiences/ 整目录复制到
   ~/.quickforge/dreaming-snapshots/<runId>/
3. for 每个会话:
     起一轮独立的 agent（systemPrompt = 整理员提示词，
     工具 = 上面四个，别的一个都没有）
4. 扫一遍目录重建 index.md
5. 记一条 run
```

四个决定及理由：

**一次一个会话。** 旧实现把所有会话合成一份 10 万字符的 transcript 交给一次调用，模型要同时兼顾所有会话，还得在脑子里做去重。改成一次一个之后，上下文短、任务明确，某个会话处理失败也只是这一轮的一条记录，不影响其他。

**串行、从旧到新。** 并行会同时改同一批文件；而从旧到新是工作真实发生的顺序——前面的会话立下笔记，后面的会话修正它。

**整目录快照，先拍再改。** 整理员有写权限，所以「搞砸了」必须是可恢复状态。快照失败就整轮不跑：一个能改记忆却没有回头路的 agent，比一晚上不整理更糟。

**它是 agent，不是流水线。** 「哪些笔记重复了、该合并成哪一篇、这次值不值得沉淀成经验」这类判断没有可靠的规则形式，写死的规则只会在边界上出错。所以给它工具和准则，让它自己决定；代价是每次结果不完全一样，换来的是它能处理没预设过的情况。

### 整理员的准则（`server/dreaming/prompt.mjs`）

- **只负责一个会话**，看不到别的会话，不许推测。
- 动手前先 `list_memory_notes`，已有同类就改写那篇，不加近似重复。
- 文件名和结论不一致时必须改名。
- 不删，只归档。
- 一轮最多写 5 篇、每篇最多 4000 字符，写不完留给下一轮。
- 沉淀成经验的门槛：同一做法在 3 篇以上的工作记忆或会话里出现过，**或者**只出现过一次但解法明确、步骤清楚。
- 建新经验前先读索引，已有近似条目就更新它。
- 写 front matter：`title` 与文件名逐字相同（写入层会拒），`description` 写「什么时候该打开这篇」，`general` 只回答「换个项目能不能照做」。
- 不许碰 `skills/`；`candidate_skill: true` 只在 `general: true` 时成立。

## 8. 失败与回滚

| 情况 | 行为 |
| --- | --- |
| 快照失败 | 整轮不执行，run 记为 failed |
| 某个会话的模型调用失败/超时 | 记一条失败，继续下一个；全部失败才算整轮 failed |
| 时间预算（45 分钟）用尽 | 在会话边界停下，剩下的留到下一轮，run 记 `stopped` |
| 用户要回滚 | `POST /api/dreaming/runs/:id/restore` 用那一轮的快照整目录覆盖回来 |

快照保留最近 10 轮。

## 9. 退役清单

| 东西 | 处理 |
| --- | --- |
| `~/.quickforge/DREAMING.md` | 删除。内容分流：机制自述类直接删，可复用的搬进经验库，项目细节搬进工作记忆 |
| `recall_experience` 工具 | 删除。索引在系统提示词里，要看细节直接 `read_memory_note` |
| `server/dreaming/notes.mjs`、`recall.mjs` | 删除 |
| `dreaming_note_stats` 表 | 保留不动（不迁移 = 不冒险），但已无写入方 |
| `dreaming-settings` 的 `prune*` 四项 | 删除。剪枝依赖「召回次数」，而召回工具已经没了 |

## 10. 已知取舍

- **索引按更新时间排序**，不是按重要性。经验超过 80 条时，重要的旧条目会掉出索引。当前选择是「宁可掉出去，也不让每个会话背着全部索引」。
- **没有「这条经验被用过几次」的统计**。曾经有过（`dreaming_note_stats`），但那需要一次显式的召回调用；现在细节读取走的是通用的读文件工具，统计就得污染通用路径。等真的有需要再加。
- **系统提示词只在新建会话时重建**。新写的经验要等下一个会话才出现在索引里，不会中途热更新。
- **整理员质量取决于模型**。给的是准则而不是硬规则，所以同样的会话跑两次可能得到不同笔记。这是有意的：换成规则引擎，遇到没预设过的情况会直接崩。
- **工作记忆是全局共享的**，不按项目隔离。项目细节靠文件名自己带上下文（例如「quickforge 项目构建约 9 秒」）。
