为什么这次不再画房间

v1–v6 是同一个大类里的六次迭代：剖面办公室 → 俯视桌面 → 夜班 → 深夜工作室 → 丁达尔舞台。每次都更好看，但类没换过。

1. 旧方向与项目设计语言冲突

DESIGN_LANGUAGE.md：工具感——保持开发者工具的效率感，不做过度拟物或娱乐化视觉；背景保持干净；为了"高级感"加入不必要的渐变属于设计禁忌。
  • 工作台是硬编码深色 #0e1015，与浅色 token 体系（--background: oklch(1 0 0)）直接冲突，深浅切换时像另一款产品。
  • 丁达尔光、尘埃、天空四层 crossfade 都是纯装饰；按设计语言应删。
  • 四段表演位（ACTOR_SLOTS）只放得下 4 只 bot，第 5 只挤进 slot3 与第 4 只重叠——这是装饰结构决定信息结构。

2. 换向：工作台 = 调度视图，不是场景

用户打开工作台只想知道三件事。新结构直接对应这三个问题，而不是对应"一间办公室"：

问题答案落在哪
谁在干活？行内状态列：在跑 · 2 分 12 秒／待命／心跳已关闭
接下来谁会醒？行内轨道：实心点＝已发生，空心点＝按 nextRunAt + intervalMinutes 外推的预测
哪里卡住了？红色状态点 + 行内错误摘要，展开看 lastError 与连续失败次数

mascot 没有删，但降为 22px 的身份标记——它是"这是哪只 bot"的识别符，不再是舞台演员。

3. 数据可行性（设计稿不画假能力）

界面元素数据来源状态
状态 / 心跳参数 / 下次唤醒GET /api/bots 的 busy,status,heartbeat.*现成
已发生的心跳点只能从 lastWakeAt 按 intervalMinutes 向前回推近似
预测的心跳点nextRunAt 按间隔外推现成
失败 / 跳过标记只有最近一次的 lastError / lastIdleReason；历史序列需服务端加环形记录，或前端会话内累积需补
定时任务条GET /api/scheduled-tasks（含最近 5 条 runs）+ /api/scheduled-tasks/runs现成
展开里的目标GET /api/agents/:sessionId/status 的 goal现成
展开里的记忆片段GET /api/bots/:id/memory现成

注意 N+1：首屏只有一次 /api/bots；goal 与 memory 只在展开某一行时才按需请求。不要在渲染 5 只 bot 时打 10 个请求。

4. 落地拆解（不改宿主文件）

  • 重写 src/components/workbench/Workbench.tsx + workbench.css，WorkbenchPortal 对外签名不变 → ConversationHeader.tsx 零改动。
  • 颜色改吃全局 token，删除硬编码 --wb-*；深浅主题自动跟随，不用再做一套。
  • 复用 botStatusSummary()（src/components/bots/bots-data.ts）出状态文案与色档，不新增状态判定逻辑。
  • 入口图标 Theater → 换成调度语义（如 LayoutList / GanttChart），并沿用同一个 workbenchTitle 文案键。
  • i18n 需要新增约 12 个键（在跑 / 待命 / 心跳关闭 / 每 N 分钟 / 下次 / 进会话 / 只看有问题的 / 6 小时 / 24 小时 / 目标 / 记忆 / 需要处理）。旧的 4 个时段键（dawn/day/dusk/night）可删。

5. 我推荐哪个

主方案（班表）：信息密度最高、每行都对应真实数据、能同时回答三个问题，且是三个方案里最省实现成本的（一张 grid + 一条绝对定位轨道，无图表库）。

网格墙：bot 超过 8 只时更耐看，但每张卡能放的信息少，且卡片化与"避免重卡片"的约束有张力，需要严格压到 1px 边框 + 零阴影。

指挥台：适合深挖单只 bot，但与设置页三栏观感重复，且把它当"工作台"等于让用户先选一只 bot，先答错了问题。

6. 需要你拍的三件事

  • 方向：班表 / 网格墙 / 指挥台，还是"班表为主、行展开吸收指挥台"。
  • 工作台是否保留深色独立空间：我建议跟随主题，不再单独深色。
  • 心跳历史：先接受"按间隔回推的近似点"，还是这轮就加服务端环形记录（约 1 个字段 + 一次写入）。
